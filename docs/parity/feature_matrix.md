# TavernCanvas Feature Parity Matrix

Machine-checked ledger mapping every observable legacy (SillyTavern-extension v2.8.1) user
workflow to its TavernCanvas v3 disposition. Checked by `tools/parity_check`
(`node tools/parity_check/dist/index.js docs/parity/feature_matrix.md`), which cross-verifies
this file against the frozen ground truth in `tools/parity_check/src/legacy_inventory.ts`.

### Parse format (consumed by `tools/parity_check/src/parse_matrix.ts`)

Each of the 18 groups below is a `## {group name}` heading (verbatim group names from the Stage
07 task brief) immediately followed by a GitHub-flavored Markdown table with exactly six columns,
in this order:

```text
ID, V2 Entry, V3 Owner, Status, Acceptance Test, Notes
```

- **ID** -- stable, unique, non-empty. Cross-checked 1:1 against `legacy_inventory.ts`.
- **V2 Entry** -- legacy module path plus function/selector name (from the bundled v2.8.1
  `index.js`, one comment-marked module per original source file) or, for `html/settings/*.html`
  panels, the file itself.
- **V3 Owner** -- the v3 file (existing or a task's not-yet-implemented, exact future path) that
  is or will be responsible for this workflow.
- **Status** -- exactly `ported` or `removed_approved`. No other value is accepted;
  `pending`/`partial`/`planned`/blank are release failures the checker rejects.
- **Acceptance Test** -- a repo-relative path to a test file. The checker requires the file to
  exist on disk (it does not run the test).
- **Notes** -- free text. A `removed_approved` row's Notes cell MUST open with one of the fourteen
  closed-list tags (`[global-error-collector]`, `[steganography-sync-db]`,
  `[vendored-umd-patches]`, `[custom-css-injector]`, `[ua-capability-detection]`,
  `[client-controlled-provider-url]`, `[reversible-pseudo-encryption]`,
  `[worldinfo-tool-injection]`, `[last-message-attachment-fallback]`,
  `[duplicate-in-app-updater]`, `[cache-completion-flags]`,
  `[non-redistributable-content-default-bundle]`, `[decorative-flourish-out-of-scope]`,
  `[voice-features-out-of-scope]`) so the checker can verify the removal
  is on the closed approved list (task brief Step 2) rather than trust free-form prose.

### Placeholder acceptance-test convention

Rows whose real acceptance test lands in a later Stage 07 task (T2-T7) point at that task's exact
future test file path, taken verbatim from
`docs/superpowers/plans/2026-08-04-tavern-canvas-07-parity-release.md`'s per-task file list. This
commit creates each such file as a minimal, real, committed test (`describe.todo(...)` naming the
owning task and the behavior it will assert) so `tools/parity_check`'s "every acceptance-test file
exists" rule passes today. The owning task extends that same file in place; it does not need to
create a new one. Placeholder files live at the exact path the owning task's plan already names,
so nothing needs to move later. Rows whose behavior is already implemented (Stage 01-06) instead
point at the real, already-passing test file that exercises it.

### Known scope gaps (flagged, not silently absorbed)

A few legacy groups have no file explicitly named in any Stage 07 task's plan. These rows are
still marked `ported` (per the Stage 07 controller's carry-over instruction: no-owner-yet rows are
`ported` with the closest named module + a placeholder test, not left `pending`), with an honest
note on every affected row:

- **LLM connection/profile management** (`LLM prompt generation and testing` group): v3's
  `ProviderId` enum (`packages/contracts/src/provider.ts`) only names the 5 image providers; no
  file manages a generic text-generation LLM connection. Assigned to T2's `prompt_pipeline.ts`
  (whose own plan text says it makes "prompt-building private LLM calls"), but T2's file list does
  not enumerate an LLM-profile file. Needs an explicit decision from whoever scopes T2.
  `assistant.*` AI-authored buttons use the assistant's own T5-owned connection instead.
  Additionally, `llm.image_send_toggle`-style rows in `LLM prompt generation and testing` are
  distinct from the near-identical `assistant.history_image_handling` in the AI-assistant group --
  same pattern, two different LLM connections in v2 (image-prompt-assist vs. the assistant chat).
- **Gesture drawing and click-trigger** (`regular-expression and click/drawing triggers` group):
  no T2-T7 file names gesture/drawing/click-trigger handling explicitly. Assigned to T2's
  `trigger_parser.ts` as the closest thematic fit (this group's own name is "click/drawing
  triggers"); needs confirmation from whoever scopes T2.
- **NSFW vocabulary group-tree default-load** (`vocabulary import, grouping, search, and update`
  group): recorded `ported` rather than `removed_approved` because "non-redistributable bundled
  content" is not one of the eleven closed-list removal categories; see that row's Notes.
